# Интеграция amoCRM

Клиент — `ingest/amo_client.py` (API v4, **долгосрочный Bearer‑токен**, без OAuth‑обмена). Домен и токен задаются в «Настройки → amoCRM». Проверка — кнопка «Проверить подключение» (`test_connection` → `get_account`).

## 1. Импорт звонков (`ingest/amo_source.py`)
- `poll_amo(app)` опрашивает примечания `call_in`/`call_out` по контактам или сделкам (`AMO_ENTITY`), окно — `amo_since_days`/`POLL_INTERVAL_MIN`, мин. длительность — `amo_min_duration`.
- **Дедуп** по `amo_note_id` (unique).
- Привязка **менеджера**: `User.amo_user_id` ↔ `responsible_user_id`. Привязка **клиента**: по нормализованному телефону.
- Скачивание записи в Volume (`download_recording_to_volume`); для Мегафона (megapbx.ru) иностранные IP блокируются — нужен РФ‑прокси (`RECORDING_PROXY`).
- Далее — общий пайплайн обработки.
- Диагностика: «Диагностика (что отдаёт amoCRM)» (`debug_recent_notes`), «Синхронизировать пользователей» (`sync_users` — проставляет `amo_user_id` по email).

## 2. Импорт сделок (`ingest/amo_deals.py`)

### Как определяется выигрыш/проигрыш
**Строго по системным id статусов amoCRM:**
- `142` = «успешно реализовано» (**won**),
- `143` = «закрыто и не реализовано» (**lost**).

Эти id менять нельзя — можно только **переименовать метку** (в текущем аккаунте `142` называется «Оплата получена»). Поле `type` статуса **не** индикатор выигрыша: `type=1` — это «Неразобранное», а не победа. Не использовать `type` для определения won/lost.

### Правила импорта
- Тянем сделки из **ВСЕХ воронок** и храним `pipeline_id`. Ограничение «только воронка X» применяется **на экране лидерборда**, а не при импорте (иначе смена воронки в настройках стирала бы реальные сделки).
- Выигранные и проигранные тянутся **раздельными запросами** (`order=desc`, свежие первыми): проигранных бывают десятки тысяч, при едином запросе они «топят» немногочисленные выигранные и те не попадают в выборку.
- Upsert по `amo_lead_id`. Импорт проигранных — батч‑коммитом.
- `won_at` = дата закрытия (`closed_at`), по ней считается месяц выручки.

### Кнопки в «Настройках» (блок «Сделки и Leaderboard»)
| Кнопка | Функция | Режим |
|---|---|---|
| ✅ Импортировать выигранные (быстро) | `import_won` | синхронно, отчёт по воронкам |
| ❌ Импортировать проигранные (в фоне) | `import_lost` | фон, батч |
| 🔎 Где лежат сделки (по воронкам) | `status_histogram` | диагностика: выигранных по каждой воронке |
| 💰 Опросить сделки | `poll_deals` | инкрементально, фон |
| ↺ Пересобрать сделки | `resync_deals` | полный пересбор, фон, безопасно (проверка связи до удаления) |

Воронка лидерборда — настройка `leaderboard_pipeline_id`.

## 3. Лидерборд и геймификация (`leaderboard/`, `amo_deals.py`)
- Рейтинг по **выручке за месяц** (сумма `price` выигранных, `won_at` в месяце, фильтр по воронке лидерборда).
- **XP**: `+50` за каждые `50 000 ₽` (`XP_STEP_RUB`, `XP_PER_STEP`).
- **Поздравления в Telegram**: `🔥 Имя ✅ ХХХ руб +ХХ Xp 🚀 Поздравляем!` Только за свежие выигрыши (≤2 дней), не на первичном бэкфилле, с лимитом на прогон, только по воронке лидерборда.
- Показываются менеджеры «Отдела продаж» **и** любой менеджер с выигрышами за месяц.

## 4. Связка звонок ↔ сделка (исход) — `processing/lead_score.py`
- `call_outcome(call, by_contact, by_lead)`: сначала по лиду (`amo_entity_type=='leads'` → `amo_entity_id`), затем по контакту (`client.amo_contact_id` или `amo_entity_id`).
- `outcome_lookup(contact_ids, lead_ids)`: выбирает **только** сделки по id показываемых звонков (иначе на больших аккаунтах тянулась вся таблица `deals` и «Звонки» вешались).
- Используется фильтром «успех/закрыто» в «Звонках» и скорингом лида.

## 5. Известные нюансы
- Звонки и сделки могут висеть на **разных контактах** amoCRM → фильтр по исходу в «Звонках» пуст. Кандидат на матчинг по телефону, а не только по `amo_contact_id`.
- Открытые вопросы: формат `LINK` в примечании, маппинг `User.amo_user_id`, по какой сущности тянуть звонки — добиваются по факту.
