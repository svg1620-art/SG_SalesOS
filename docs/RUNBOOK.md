# Runbook — эксплуatация, диагностика, грабли

Практическое руководство: типовые операции и разбор реальных инцидентов с решениями.

## Типовые операции

### Наполнить лидерборд из amoCRM
1. «Настройки → Сделки и Leaderboard»: выбрать **Воронку для лидерборда** → «Сохранить».
2. Нажать **✅ Импортировать выигранные (быстро)** — дождаться отчёта («добавлено N, по воронкам …»).
3. (опц.) **❌ Импортировать проигранные (в фоне)** — для скоринга/фильтра исхода.
4. Открыть «Leaderboard», выбрать месяц.
5. Если у части сделок нет менеджера — «Синхронизировать пользователей» (свяжет по email), затем импорт выигранных повторно.

### Проверить, где лежат победы
«Настройки → 🔎 Где лежат сделки (по воронкам)» — точный подсчёт выигранных (статус 142) по каждой воронке. Если победы не в целевой воронке — переключить воронку лидерборда.

### Перезапустить обработку звонка
Карточка звонка → «Переоценить». Вариант «по чек‑листу отдела (авто)» сбрасывает `checklist_id=None`, воркер переразрешает чек‑лист по отделу менеджера.

### Сменить провайдера транскрибации/анализа
«Настройки → Транскрибация» / «Настройки → Анализ (LLM)». Откат мгновенный (вернуть провайдера обратно).

## Разбор инцидентов (реальные, с решениями)

### «Звонки»/«Диалоги» не открываются (висят)
**Причина:** N+1 запросы — ленивая загрузка `client`/`manager` на каждую строку списка; плюс полная выборка таблицы `deals` для исхода.
**Решение (уже в коде):** `joinedload(client, manager)` в списках; `outcome_lookup(contact_ids, lead_ids)` — только по id показываемых звонков; лимит выборки (звонки — `.limit(2000)`, показ 500).
**Правило:** в любых списках — eager‑load связей и никогда не тянуть большую таблицу целиком на каждый рендер.

### «Модель вернула не JSON‑объект анализа» на длинных звонках
**Причина:** ответ LLM обрезался по лимиту токенов; верхний объект `{…}` не закрывался, `extract_json` возвращал вложенный массив (не dict).
**Решение (в коде):** анализ с `max_tokens=8000` и `require_complete=True` (честная ошибка про обрезку вместо запутывающей).

### Лидерборд пуст / «подтягиваются только два этапа»
**Причина 1:** выигрыш определяли по `type` статуса — но `type=1` это «Неразобранное», а не победа.
**Причина 2:** в аккаунте десятки тысяч проигранных (143) — при едином запросе выигранные (142) не помещались в выборку.
**Причина 3:** импорт был ограничен одной воронкой, а пересбор удалял сделки других воронок.
**Решение (в коде):** выигрыш/проигрыш строго по id `142`/`143`; выигранные и проигранные тянутся раздельными запросами; импорт из всех воронок, фильтр воронки — на экране лидерборда.

### Страница диагностики «Где лежат сделки» висела
**Причина:** синхронный веб‑запрос тянул и проигранные (десятки тысяч, до 40 страниц API).
**Решение:** диагностика считает только выигранные (142) — их сотни, открывается за секунды.

### Транскрибация «двумя блоками», а не диалогом
**Причина:** `gpt-4o-transcribe` не отдаёт посегментные тайминги.
**Решение:** нарезка каналов по паузам и склейка по времени (OpenAI‑путь); либо Deepgram `multichannel` (один запрос, точные тайминги).

### Дашборд «за прошлый день» / неверный месяц выручки
**Причина:** границы суток считались в UTC; месяц брался по `updated_at`.
**Решение:** TZ‑aware границы (Europe/Moscow, `utils.py`); месяц выручки — строго по `won_at` (дата закрытия).

## Диагностические инструменты в «Настройках»
- **Проверить подключение** amoCRM (`get_account`).
- **Диагностика (что отдаёт amoCRM)** — сырые примечания.
- **🔎 Где лежат сделки (по воронкам)** — распределение выигранных.
- Строки статуса: «Последний опрос сделок», «Последний импорт проигранных», связка «звонок ↔ сделка».

## Грабли, которые легко повторить
- Изменить связку `openai`/`httpx` → краши. Держать пины из `requirements.txt`.
- Задеплоить >1 воркера → APScheduler задвоит пульс/сводку/опрос.
- Деплой не в EU → нет доступа к Anthropic API.
- Переменные Railway блоком/с кавычками → склеенные/битые значения.
- Полная выборка большой таблицы в списке → зависание (см. выше).
