# Разнесение планировщика: сервис `worker` на Railway

Цель — убрать фоновые джобы (синхронизация метрик, LLM-диагностика, продления,
Telegram-чекпоинты) из веб-процесса, чтобы они не тормозили запросы. Веб-сервис
остаётся с Volume и аудио-пайплайном, тяжёлое уходит на отдельный `worker`.

## Почему именно так (важное ограничение Railway)

`amo_poll` скачивает записи звонков в Volume `/data`, а веб отдаёт их плеером из
того же `/data`. **Volume в Railway монтируется только к ОДНОМУ сервису.**
Поэтому нельзя просто унести весь планировщик — иначе сломается плеер.

Решение — переменная `SCHEDULER_ROLE`:

| Роль | Какие джобы | Volume |
|---|---|---|
| `web` | только `amo_poll` (скачивание записей + транскрибация) + плеер/ручная загрузка | нужен |
| `worker` | всё остальное: `ops_sync`, `ops_recompute_yesterday`, `ops_generate_missions`, `ops_alerts`, `ops_diagnosis`, `renewals_sync`, `renewals_classify`, `telegram_pulse`, `daily_digest`, `tg_poll`, `tg_mission`, `tg_cp_morning`, `tg_cp_afternoon`, `tg_finish` | не нужен |
| `all` | обе группы в одном сервисе (текущее поведение, дефолт) | нужен |

`web` остаётся с `--workers 1`: он всё ещё держит `amo_poll`, а при нескольких
воркерах планировщик бы задвоился. Весь тяжёлый LLM/аналитический фон уходит на
`worker`, поэтому веб разгружается даже на одном воркере.

## Порядок внедрения (без двойных отправок)

Переключаем в таком порядке, чтобы ни один момент джобы не работали в двух
местах сразу (иначе — двойные сообщения в Telegram и двойные записи в amo).

1. **Задеплоить код** (уже в `main`): появились `worker.py` и `SCHEDULER_ROLE`.
   Пока ничего не меняется — текущий единственный сервис работает как `all`.

2. **Перевести текущий веб-сервис в роль `web`.** В его Variables:
   - `SCHEDULER_ROLE=web`
   - `SCHEDULER_ENABLED=1` (как и было)
   Redeploy. Теперь веб крутит только `amo_poll`; аналитический фон временно
   не идёт — это нормально, несколько минут без синка не страшно (лучше, чем
   двойные отправки).

3. **Создать второй сервис `worker`** в том же проекте Railway из того же репозитория:
   - **New → GitHub Repo → тот же репозиторий/ветка**, что и веб.
   - **Settings → Deploy → Custom Start Command:** `python worker.py`
   - **Volume НЕ подключать.** (`/data` остаётся только у веба.)
   - **Variables** (скопировать с веба, значения те же):
     - `DATABASE_URL` — тот же, что у веба (та же БД; на Railway удобно через
       Reference Variable на Postgres-плагин).
     - `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `CLAUDE_MODEL`,
       `OPENAI_TRANSCRIBE_MODEL`, `TZ`, amoCRM-переменные, `TELEGRAM_*`, `SECRET_KEY`.
     - `SCHEDULER_ROLE=worker`
     - `SCHEDULER_ENABLED=1` (worker.py выставит сам, но лучше явно).
   - Регион — **EU** (как и веб: доступ к Anthropic).
   - Миграции на worker НЕ запускаются (их катит веб командой `flask db upgrade`).
     Start command у worker — именно `python worker.py`, без `db upgrade`.

4. **Проверить логи worker:** строка `[worker] старт: роль=worker, джоб=14 [...]`.
   В логах веба при деплое — `[scheduler] роль=web, джоб=1 ...`.

## Проверка, что всё работает

- Веб: открывается, плеер звонка играет (аудио на месте), ручная загрузка пишет в `/data`.
- Worker: в логах видно срабатывания `ops_sync` (раз в 5 мин), `tg_poll` (2 мин).
- Привязка Telegram (`/start КОД`) отвечает — её обрабатывает `tg_poll` на worker.
- Метрики на `/ops/board` обновляются (их считает `ops_sync` на worker).

## Откат

Вернуть веб-сервису `SCHEDULER_ROLE=all` (или убрать переменную — дефолт `all`)
и остановить/удалить `worker`. Один сервис снова делает всё.

## Нюансы

- **Смена часов пульса/сводки в «Настройках»** перепланирует джобы только в том
  процессе, где нажали «Сохранить» (веб, роль `web`). Воркерные `telegram_pulse`/
  `daily_digest` подхватят новые часы после рестарта `worker` (Redeploy).
- **Полностью stateless (на будущее):** если перенести хранение аудио из Volume
  в объектное хранилище (S3/Cloudflare R2), Volume станет не нужен, `amo_poll`
  тоже уедет на `worker`, а веб можно будет масштабировать на несколько воркеров.
  Это отдельная задача (бэкенд хранения записей read/write + миграция файлов).
