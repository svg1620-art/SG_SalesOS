# SG_SalesOS — Модуль «Операционный пульт» (Ops Metrics + Daily Missions + Payback)

Техническое задание на расширение SG_SalesOS. Документ для Claude Code: читать целиком перед началом любого этапа, реализовывать строго по этапам (один этап = один деплой на Railway).

Связанные документы: `OVERVIEW.md`, `CLAUDE.md`, `SG_SalesOS_spec.md`, `docs/DATA_MODEL.md`, `docs/AMOCRM.md`.

---

## 0. Зачем этот модуль

Сейчас SG_SalesOS отвечает на вопрос **«как менеджер говорит»** (качество звонка). Он не отвечает на вопросы:

1. **«Сколько и как ритмично он работает»** — попытки, дозвоны, касания, сообщения, распределение по часам.
2. **«Где у него рвётся воронка»** — квалификация → встреча назначена → встреча проведена → счёт → оплата, в сравнении с командой и с самим собой.
3. **«Окупает ли он себя»** — помесячно и накопительно, с объяснением, *почему* в этом месяце окупил, а в следующем нет.
4. **«Как сделать, чтобы менеджеру хотелось работать»** — при систематическом невыполнении месячного плана дофамин от плана отсутствует. Нужна ежедневная, достижимая, контролируемая самим менеджером цель с мгновенной обратной связью.

### Управленческая логика (обязательна для понимания)

Метрики делятся на три слоя. Менеджер напрямую управляет только первым, поэтому ежедневная мотивация строится на первом слое, а второй и третий открываются по мере роста.

| Слой | Что | Кто управляет | Горизонт |
|---|---|---|---|
| **L1. Ритм (активность)** | дозвоны, касания, сообщения, время в разговоре | полностью менеджер | час / день |
| **L2. Воронка (операционные)** | квалификации, встречи назначены/проведены | менеджер + клиент | день / неделя |
| **L3. Результат** | счета, оплаты, выручка, окупаемость | менеджер + клиент + цикл сделки | месяц |

Принцип: **«ежедневно выигрываемая игра на L1 → разблокировка L2 → результат на L3»**. Месячный план не отменяется, но перестаёт быть единственным источником обратной связи.

## 1. Состав модуля (что строим)

1. **Сбор активности из amoCRM** — инкрементальная синхронизация событий (звонки, сообщения, смены этапов, задачи) в собственную таблицу событий.
2. **Движок метрик** — расчёт дневных/часовых агрегатов по менеджеру и команде.
3. **«Мой день»** — экран менеджера: дневная миссия, прогресс, тепловая карта по часам, серия, уровень.
4. **«Оперативный пульт РОПа»** — таблица менеджеров «здесь и сейчас», светофоры, алерты, прогноз выполнения плана.
5. **Воронка и конверсии** — сравнение менеджеров между собой и с собственной историей.
6. **Окупаемость (Payback)** — помесячно, накопительно, прогноз; **факторная диагностика просадки**.
7. **Дневные миссии и геймификация** — уровни, тиры Bronze/Silver/Gold, серии, личные рекорды, расширение существующего XP.
8. **Telegram‑триггеры** — личные уведомления менеджеру, чекпоинты РОПу.
9. **AI‑диагностика** — еженедельный разбор «что происходит с менеджером» на основе цифр + качества звонков.

## 2. Словарь метрик (единые определения)

Все определения реализуются в одном месте — `services/metrics/definitions.py`. Пороги — в настройках (таблица `ops_settings`), не хардкодом.

### L1 — Ритм

| Код | Название | Определение |
|---|---|---|
| `calls_out` | Исходящие попытки | Все исходящие звонки менеджера (любой статус, любая длительность) |
| `calls_connected` | Дозвоны | Исходящие + входящие звонки с длительностью ≥ `connect_min_sec` (по умолчанию **30 с**) |
| `connect_rate` | Доля дозвона | `calls_connected_out / calls_out` |
| `talk_time_min` | Время в разговоре | Сумма длительностей дозвонов, мин |
| `messages_out` | Сообщения | Исходящие сообщения в чатах amoCRM (WhatsApp/Telegram/и т.д. через «Чаты» amoCRM) |
| `touches` | Касания | Число **уникальных клиентов (контактов)**, с которыми за день было ≥1 результативное действие: дозвон ИЛИ исходящее сообщение ИЛИ проведённая встреча |
| `new_leads_contacted` | Обработка новых | Новые лиды, получившие первое касание за день |
| `speed_to_lead_min` | Скорость реакции | Медиана минут от создания входящего лида до первого исходящего действия (только рабочие часы) |
| `first_action_at` / `last_action_at` | Начало / конец дня | Время первого и последнего исходящего действия |
| `idle_gaps` | Простои | Интервалы ≥ `idle_gap_min` (по умолчанию 60 мин) без действий внутри рабочих часов |
| `tasks_overdue` | Просрочки | Открытые просроченные задачи в amoCRM на конец дня (гигиена CRM) |

### L2 — Воронка

| Код | Название | Определение |
|---|---|---|
| `qualified` | Квалификации | Переход лида в этап, помеченный в маппинге как `qualified` |
| `meetings_set` | Встречи назначены | Переход в этап `meeting_set` |
| `meetings_held` | Встречи проведены | Переход в этап `meeting_held` |
| `show_rate` | Доходимость | `meetings_held / meetings_set` (по когорте назначенных за период) |

### L3 — Результат

| Код | Название | Определение |
|---|---|---|
| `invoices` | Счета | Переход в этап `invoice` (кол-во + сумма бюджета сделки) |
| `payments` | Оплаты | Сделка в статусе 142 (кол-во + сумма) — уже существует в SalesOS |
| `first_revenue` | Первая выручка | Оплата, которая является **первой выигранной сделкой клиента** (см. §8.0). Повторные оплаты того же клиента сюда не входят |
| `avg_check` | Средний чек | `first_revenue_sum / first_revenue_count` |
| `plan_progress` | Выполнение плана | `first_revenue_sum_mtd / revenue_plan` |
| `plan_forecast` | Прогноз плана | `first_revenue_sum_mtd + Σ(invoice_sum × CR_invoice→payment) + run-rate остатка месяца` (см. §7.4) |
| `payback_ratio` | Окупаемость | см. §8 |

### Конверсии (считаются по команде и по каждому менеджеру)

```
дозвон → квалификация → встреча назначена → встреча проведена → счёт → оплата
```

Для каждой ступени: значение за период, медиана команды, собственная медиана за 90 дней, отклонение.

**Важно:** конверсии по ступеням считаются **когортно по лиду** (лид вошёл в ступень N в периоде → дошёл ли до N+1 в пределах `cohort_window_days`, по умолчанию 45), а не делением «количества за месяц на количество за месяц». На экране показываем оба варианта с подписью: «когортная» (основная) и «потоковая» (быстрая оценка).

## 3. Источники данных и интеграция с amoCRM

### 3.1. Что тянем

| Что | Откуда (amoCRM API v4) | Примечание |
|---|---|---|
| Звонки | `GET /api/v4/events` с типами `outgoing_call`, `incoming_call` + примечания `call_in`/`call_out` (длительность, статус, ссылка на запись) | Записи от Мегафона уже приходят как примечания — переиспользовать текущий код SalesOS |
| Сообщения | `GET /api/v4/events` с типами `outgoing_chat_message`, `incoming_chat_message` | Менеджеры пишут клиентам через «Чаты» amoCRM — это полноценный источник касаний |
| Смены этапов | `GET /api/v4/events` тип `lead_status_changed` | Основа L2/L3 |
| Задачи | `GET /api/v4/tasks` (выполненные/просроченные, тип задачи) | Для просрочек и, опционально, встреч |
| Лиды | `GET /api/v4/leads` (responsible_user_id, pipeline_id, status_id, price, created_at, closed_at) | Для атрибуции и сумм |

### 3.2. Режим синхронизации

- **Инкрементально** каждые `sync_interval_min` (по умолчанию **5 минут**) через APScheduler: курсор по `created_at` последнего обработанного события, с перекрытием 10 минут (защита от поздно записанных событий), дедупликация по `amo_event_id`.
- **Бэкфилл** при первом запуске: 90 дней назад, пакетами, с прогрессом на странице «Синхронизация».
- Rate limit amoCRM (7 req/s) — соблюдать; exponential backoff на 429/5xx (как в остальных проектах SG).
- Падение одного пакета не роняет синхронизацию (failure isolation), ошибка пишется в `ops_sync_log`.

### 3.3. Атрибуция действий менеджеру

- **Звонок/сообщение** → `created_by` события (кто совершил). Если `created_by = 0` (робот/интеграция) — берём `responsible_user_id` контакта/лида на момент события.
- **Смена этапа (квал/встреча/счёт/оплата)** → `responsible_user_id` лида **на момент события** (а не текущий ответственный). Для этого храним снимок в `funnel_events.manager_id`.
- Менеджер ↔ amoCRM: существующее поле `users.amo_user_id`.
- Неактивные пользователи (снята «Учётка активна») — данные сохраняются, но исключаются из рейтингов и пульта (существующее правило SalesOS).

### 3.4. Валидационные чекпоинты Этапа 1 (до любой визуализации)

Claude Code обязан реализовать страницу `/ops/validation` (только admin), которая показывает:
1. Глубину истории `/events` — дата самого раннего полученного события по каждому типу.
2. Сколько звонков за вчера пришло с длительностью и статусом vs без.
3. Количество событий `outgoing_chat_message` по менеджерам за 14 дней (если у активного менеджера 0 — предупреждение: проверить сопоставление `amo_user_id` или права токена на чаты).
4. Сверка: количество звонков менеджера за вчера в нашей БД vs в amoCRM (выборочно по 3 менеджерам).
5. Список этапов всех воронок, ещё не размеченных в маппинге.

## 4. Маппинг воронки (настраивается в UI)

### 4.1. Экран `/ops/settings/funnel` (admin)

Таблица всех воронок и этапов amoCRM (подтягиваются через `/api/v4/leads/pipelines`). Для каждого этапа РОП выбирает шаг воронки:

`— / qualified / meeting_set / meeting_held / invoice / won / lost`

Статусы 142/143 размечаются автоматически как `won`/`lost`.

### 4.2. Правило «достижения шага»

Лид считается достигшим шага, если перешёл в этап, размеченный этим шагом, **или в любой этап дальше по порядку** (перескок этапа засчитывает пропущенные шаги, датой — датой перескока). Каждый шаг засчитывается лиду **один раз** (первое достижение), повторные возвраты не плодят дубли.

### 4.3. Встречи

Встречи фиксируются **только этапами воронки** («Встреча назначена» и «Встреча проведена» — отдельные этапы). Задачи amoCRM для подсчёта встреч не используются.

## 6. Экран менеджера «Мой день» (`/me/today`)

Главный экран менеджера при входе (вместо текущего кабинета; текущий кабинет становится вкладкой «Качество»).

### 6.1. Блок «Дневная миссия» (верх экрана, крупно)

- 3 кольца прогресса (метрики зависят от уровня, §9.2), у каждого — текущее значение и три отметки Bronze / Silver / Gold.
- Общий статус дня: «Бронза взята ✓ · до серебра 7 дозвонов».
- **Подсказка «финишной прямой»**: если до следующего тира осталось ≤ 25 % — показывать конкретное число действий.
- Обновление: HTMX‑polling каждые 60 с.
- **Момент дофамина:** при достижении тира — анимация (конфетти, CSS/JS без внешних CDN‑зависимостей кроме разрешённых в проекте), звук выключен по умолчанию, плюс опциональное личное сообщение в Telegram (§11).

### 6.2. Блок «Сегодня в цифрах»

Карточки: дозвоны / попытки (connect rate), касания, сообщения, время в разговоре, квалификации, встречи назначены/проведены, счета, оплаты. У каждой карточки — сравнение «vs мой средний день» (зелёная/красная стрелка), **а не vs лучший в команде** (снижение стресса у отстающих).

### 6.3. Тепловая карта активности

- Ось X: часы рабочего дня (`work_hours_from`–`work_hours_to`, по умолчанию 09–20).
- Ось Y: последние 10 рабочих дней (сегодня сверху).
- Ячейка: количество действий; переключатель метрики: дозвоны / попытки / сообщения / connect rate.
- Оверлей: «золотые часы команды» — часы с лучшим connect rate по команде за 30 дней (рамка у колонки).
- Реализация: Chart.js matrix‑плагин или CSS grid (предпочтительно CSS grid + HTMX — проще и надёжнее).

### 6.4. Серия, уровень, рекорды

- Серия дней 🔥 (текущая / лучшая), заморозки ❄️.
- Уровень и прогресс до следующего (§9.2).
- Личные рекорды: лучший день по дозвонам, касаниям, встречам; «Новый рекорд!» при обновлении.

### 6.5. Блок «Месяц»

- Выполнение плана (факт / план), прогноз выполнения.
- **Честная математика плана:** «Чтобы выполнить план, нужно в день: N дозвонов, M квалификаций, K встреч» (обратная воронка §9.1). Если требуемое > 2× текущего среднего — без драмы показывать: «План требует ускорения ×2.3» (и алерт РОПу, §10.3).

## 7. Оперативный пульт РОПа (`/ops/board`, admin)

### 7.1. Таблица «Сейчас»

Строка = активный менеджер (фильтр по отделу). Колонки:

| Колонка | Содержимое |
|---|---|
| Менеджер | имя, уровень, серия 🔥 |
| Старт дня | `first_action_at`; красный, если позже `late_start_time` (по умолчанию 10:00) |
| Дозвоны | факт / Silver‑норма, мини‑бар |
| Connect rate | % |
| Касания | факт / норма |
| Сообщения | факт |
| Квал / Встречи назн / пров | факт за день |
| Последнее действие | «12 мин назад»; красный, если > `idle_gap_min` в рабочее время |
| Миссия | текущий тир |
| Месяц | выполнение плана %, прогноз % |
| Качество | средний балл звонков за день (из существующего модуля) |
| Статус | светофор 🟢🟡🔴 по правилу §7.2 |

Сортировка по любой колонке, по умолчанию — по статусу (красные сверху).

### 7.2. Светофор менеджера (правило дня)

- 🔴: нет действий до `late_start_time` ИЛИ простой > 2×`idle_gap_min` ИЛИ к 15:00 выполнено < 40 % Bronze.
- 🟡: к 15:00 выполнено < 70 % Silver ИЛИ connect rate < 60 % от медианы команды.
- 🟢: иначе.

Пороги — в `ops_settings`.

### 7.3. Вкладка «Воронка и конверсии»

- Воронка команды за период + воронки менеджеров рядом (горизонтальные бары или таблица с heat‑раскраской).
- Матрица «менеджер × ступень конверсии»: ячейка = конверсия, цвет = отклонение от медианы команды.
- Переключатель «когортная / потоковая».
- Тепловая карта команды «день недели × час» по connect rate → рекомендация окон прозвона.

### 7.4. Прогноз выполнения плана

```
forecast = first_revenue_sum_mtd
         + Σ invoices_open_sum × CR(invoice→payment, 90 дней, по менеджеру; fallback — команда)
         + (avg_daily_first_revenue за последние 20 раб. дней × оставшиеся рабочие дни) × k_dedup
```
`k_dedup = 0.5` (настраивается) — чтобы не задваивать открытые счета и run-rate. Открытые счета учитываются только по сделкам, которые станут первой выручкой клиента. Показывать с подписью «оценка».

## 8. Окупаемость менеджера (`/ops/payback`, admin; менеджеру — только свой коэффициент, без чужих данных и без зарплат)

### 8.0. Первая выручка (единая база всего модуля)

Менеджеры продают предоплатами на 6 и 12 месяцев. **Во всём модуле выручка = только первая выручка от клиента**: план, прогноз плана, окупаемость, средний чек, факторная диагностика, дневные цели, XP за выручку и лидерборд по выручке. Повторные оплаты (продления, допродажи тому же клиенту) не учитываются нигде.

- Клиент = компания amoCRM, привязанная к сделке; если компании нет — основной контакт сделки. Ключ: `client_key = 'company:<id>' | 'contact:<id>'`.
- Сделка — первая выручка, если это **самая ранняя по `closed_at` сделка в статусе 142** с этим `client_key` за всю доступную историю amoCRM (не только за 90 дней бэкфилла — для проверки делается отдельный запрос выигранных сделок компании/контакта).
- Признак `is_first_revenue` вычисляется при импорте выигрыша и пересчитывается, если сделка позже вышла из 142 (откат оплаты).
- Сделка без компании и без контакта — считается первой выручкой, попадает в `/ops/validation` как «без клиента» для ручной проверки.
- Первая выручка зачисляется менеджеру, ответственному за сделку на момент перехода в 142.

### 8.1. Формулы

```
own_cost(m)       = (salary_fixed + bonus_paid) × (1 + payroll_tax_rate) + overhead + lead_cost
rop_share(m)      = allocated_cost из rop_cost_allocations (§8.4)
full_cost(m)      = own_cost(m) + rop_share(m)
margin(m)         = first_revenue_sum(m) × gross_margin_rate   -- gross_margin_rate в ops_settings, по умолчанию 1.0 (считаем по выручке)
payback_ratio(m)  = margin(m) / full_cost(m)                  -- основной показатель
payback_direct(m) = margin(m) / own_cost(m)                   -- справочно: без доли РОПа
cumulative_net    = Σ (margin − full_cost) с даты найма
```

На экране всегда видна разбивка `full_cost` на «свои затраты» и «доля РОПа».

Статусы месяца: **≥ 1.0** окупил 🟢, **0.8–1.0** на грани 🟡, **< 0.8** не окупил 🔴.

**Период адаптации:** первые `rampup_months` (по умолчанию 3) после `hire_date` — статус «Адаптация», пороги умножаются на `rampup_factor` (0.3 / 0.6 / 0.9 по месяцам).

### 8.2. Визуализация

- На менеджера: столбцы по месяцам (маржа vs стоимость) + линия накопительного результата (`cumulative_net`) — сразу видно «яму» и «выход в плюс».
- Сводная таблица: менеджер × последние 6 месяцев, ячейки = payback_ratio с цветом.
- Прогноз текущего месяца: `plan_forecast` (§7.4) × `gross_margin_rate / full_cost`.

### 8.3. Факторная диагностика «Что произошло с менеджером» (ключевая фича)

Выручка раскладывается в произведение факторов:

```
Revenue = Дозвоны × CR(дозвон→квал) × CR(квал→встреча назн) × ShowRate × CR(встреча→счёт) × CR(счёт→оплата) × Средний чек
```

Для сравнения месяца M с базой B (по выбору: прошлый месяц / собственная медиана 3 мес / медиана команды) вклад каждого фактора считается логарифмически:

```
contribution_i = ln(factor_i(M) / factor_i(B)) / ln(Revenue(M) / Revenue(B)) × ΔRevenue
```

(Σ вкладов = ΔRevenue; Revenue здесь = первая выручка). Если Revenue(M) = Revenue(B) или любой фактор = 0 — показывать таблицу факторов без разложения.

Вывод — waterfall‑график (Chart.js bar с плавающими столбцами) + текст: «Выручка −38 % к прошлому месяцу. Главный фактор — доходимость встреч (−30 п.п.), активность стабильна, чек +4 %».

**Ограничение:** у сделок есть лаг (цикл сделки). Добавить переключатель «Сдвиг активности на N дней» (по умолчанию — медиана цикла сделки команды), чтобы активность месяца сравнивалась с оплатами, которые она реально породила.

### 8.4. Страница ввода затрат `/ops/costs` (только admin)

**Вид:** таблица «сотрудник × месяц». Строки — все менеджеры отдела продаж (включая деактивированных, если они были активны в выбранном месяце) и РОП(ы). Селектор месяца сверху.

**Поля строки:** роль (менеджер / РОП), оклад, бонус фактический, ставка взносов (по умолчанию 30,2 %), накладные (по умолчанию из настроек), стоимость лидов (только для менеджеров), комментарий. Итог «Полная стоимость» считается на лету.

**Удобства:**
- Кнопка «Скопировать с прошлого месяца» (копирует оклады, ставки, накладные; бонус обнуляет).
- Пометка незаполненных строк; payback за месяц с незаполненными затратами показывается как «нет данных», а не как 0 или ∞.
- Изменения логируются (`updated_by`, `updated_at`); история правок видна по клику на строку.
- Роль РОПа задаётся здесь же (`cost_role = rop`); в месяце может быть несколько РОПов — их затраты суммируются в общий пул.

**Распределение затрат РОПа между менеджерами:**

```
active_days(manager, month) = рабочие дни месяца по work_calendar,
                              в которые менеджер был активен (между hire_date и deactivated_at),
                              минус дни из manager_absences
weight(manager)             = active_days(manager, month)
allocated_cost(manager)     = rop_pool_cost(month) × weight(manager) / Σ weight(всех менеджеров отдела продаж)
```

То есть РОП делится поровну между всеми активными менеджерами, а менеджер, который отработал полмесяца (пришёл, уволился, долго болел), получает пропорционально меньшую долю. Пересчёт `rop_cost_allocations` — при каждом сохранении затрат, изменении отсутствий/активности и ночью 1-го числа за прошлый месяц. Сумма долей всегда равна пулу РОПа (остаток от округления — менеджеру с наибольшим весом).

РОП в окупаемости как отдельная строка не участвует и в рейтингах не появляется.

## 9. Дневные миссии и геймификация

### 9.1. Как рассчитываются дневные цели (обратная воронка)

Каждое утро в 06:00 (или при первом входе) для каждого активного менеджера на рабочий день (не отпуск/больничный) генерируется `daily_missions`:

1. `need_revenue = max(revenue_plan − first_revenue_sum_mtd, 0)`; `days_left` — оставшиеся рабочие дни менеджера.
2. Конверсии и средний чек первой выручки — собственные за 90 дней (если данных < `min_sample`, по умолчанию 30 лидов, — медиана команды).
3. Требуемое в день по обратной воронке: оплаты → счета → встречи проведены → встречи назначены → квалификации → дозвоны.
4. Тиры для каждой метрики:
   - **Silver** = требуемое в день по обратной воронке (норма для плана), но не меньше `floor_silver[metric]` из настроек.
   - **Bronze** = `min(собственная медиана за 20 раб. дней, 0.8 × Silver)` — **гарантированно достижимый «личный стандарт»**.
   - **Gold** = `1.25 × Silver`.
   - Ограничитель: если Silver > `max_silver_ratio` (по умолчанию 2.0) × собственной медианы, Silver ограничивается этим значением, а разрыв уходит в алерт РОПу «план нереалистичен при текущих конверсиях» (§10.3). Задача — не убить мотивацию недостижимой нормой.
5. Тир дня = минимальный тир, достигнутый **по всем метрикам миссии** (взял серебро по дозвонам и бронзу по касаниям → день «Бронза»).

### 9.2. Уровни (разблокировка операционных метрик)

| Уровень | Название | Метрики миссии | Повышение |
|---|---|---|---|
| 1 | **Ритм** | дозвоны, касания, сообщения+дозвоны к новым лидам (`new_leads_contacted`) | ≥ Silver в 8 из последних 10 рабочих дней |
| 2 | **Воронка** | дозвоны, квалификации, встречи назначены | ≥ Silver в 8 из 10 |
| 3 | **Результат** | квалификации, встречи проведены, счета | вершина |

- Понижение: < Bronze в 6 из последних 10 рабочих дней → уровень −1 (с мягким сообщением, без публичного акцента).
- Смена уровня — событие: экран‑поздравление + Telegram + запись в `xp_ledger`.
- Уровень виден РОПу и в лидерборде.

### 9.3. Серии и заморозки

- Серия = подряд рабочих дней с тиром ≥ Bronze. Нерабочие дни, отпуск и больничный серию **не прерывают**.
- Заморозка ❄️: 1 шт. начисляется каждые 10 рабочих дней серии (максимум 2 в запасе); автоматически тратится на день без Bronze, сохраняя серию.
- Бейджи серий: 5 / 10 / 20 / 40 дней.

### 9.4. XP (расширение существующего)

Существующее правило «+50 XP за каждые 50 000 ₽ выручки» сохраняется и переносится в `xp_ledger`, **но база меняется на первую выручку**. Существующий лидерборд по выручке SalesOS также переводится на первую выручку (`is_first_revenue = true`); поздравление в Telegram — только за первую выручку. Добавляется:

| Событие | XP |
|---|---|
| День Bronze / Silver / Gold | +10 / +20 / +35 |
| Квалификация | +5 |
| Встреча назначена / проведена | +10 / +20 |
| Счёт выставлен | +25 |
| Новый личный рекорд | +15 |
| Повышение уровня | +100 |
| Бейдж серии | +20 / +40 / +80 / +150 |

Все значения — в `ops_settings`. Начисление идемпотентно (`UNIQUE(source, ref)`).

Лидерборд получает вкладку **«XP за неделю»** — рейтинг, в котором отстающий по выручке менеджер может быть первым за счёт процесса. Существующий рейтинг по выручке остаётся.

### 9.5. Командный квест недели

РОП задаёт в настройках недельную командную цель (например, «40 проведённых встреч»). Прогресс-бар на «Моём дне» и в пульте. При достижении — сообщение в общий Telegram‑чат и +50 XP каждому активному участнику, внёсшему ≥ 1 шаг. Задача — добавить чувство команды, а не только конкуренцию.

### 9.6. Анти‑накрутка (обязательно)

- Дозвон засчитывается при длительности ≥ `connect_min_sec`.
- В миссию идёт не более `max_calls_per_contact_day` (по умолчанию 3) звонков одному контакту в день.
- Сообщения засчитываются в касания только как уникальный контакт в день; в `messages_out` — не более 10 на контакт в день.
- Квалификация/встреча, откатанная назад (лид вернули на этап раньше) в течение 24 ч, — XP списывается (отрицательная запись в `xp_ledger`).
- **Quality gate:** если средний балл звонков менеджера за день < `quality_gate_score` (по умолчанию 60) при ≥ 3 оценённых звонках — тир дня ограничивается Silver (Gold недоступен). Связка с текущим ОКК.

## 11. AI‑диагностика менеджера (еженедельно)

- Понедельник 08:00: для каждого активного менеджера Claude Sonnet получает JSON с: метриками L1–L3 за 4 недели, конверсиями vs команда, результатом факторной диагностики (§8.3), трендом балла качества, топ‑3 повторяющимися упущенными моментами из ОКК, историей уровней/серий.

## 14. Нефункциональные требования

- Стек проекта: Flask + Jinja2 + HTMX + PostgreSQL (SQLAlchemy) + APScheduler + Chart.js. Новых фреймворков не вводить.
- Railway **EU‑регион** (обязательно). `DATABASE_URL` — только через reference variable.
- Код модуля — в `services/ops/` (sync, metrics, missions, payback, alerts, diagnostics) и `blueprints/ops.py`. Бизнес‑логика в сервисном слое, роуты тонкие.
- События модуля (тир достигнут, уровень, алерт) — через существующий `emit_event()`.
- Failure isolation: падение синхронизации, расчёта миссий или AI‑диагностики по одному менеджеру не останавливает остальных.
- Внешние вызовы (amoCRM, AI, Telegram) — exponential backoff.
- Все джобы идемпотентны (upsert, уникальные ключи).
- Производительность: «Мой день» и пульт отдают ответ < 500 мс на 20 менеджеров — читать только из `manager_day_stats` / `manager_hour_stats`, не из `activity_events`.
- UI: бренд‑токены SG (тёмная база `#0A0A0D`, синий `#1467F5`, циан `#00BFDC`, Manrope, цифры — JetBrains Mono). Оранжевый не использовать. Mobile‑friendly «Мой день» (менеджеры смотрят с телефона).
- Существующий функционал SalesOS (ОКК, дашборд, лидерборд, пульс) не ломать; при изменении существующих файлов — выдавать **полные версии файлов**, а не диффы.

## 15. Этапы реализации (1 этап = 1 деплой)

**Этап 1. Сбор данных и валидация**
Таблицы `activity_events`, `funnel_stage_map`, `funnel_events`, `ops_settings`, `ops_sync_log`, `work_calendar`. Синхронизация событий (инкремент + бэкфилл 90 дней), экран маппинга воронки, страница `/ops/validation` (§3.4).
*Чекпоинт:* глубина истории событий, наличие длительностей звонков, наличие событий чатов, сверка количества звонков с amoCRM.

**Этап 2. Движок метрик + «Мой день» (без миссий)**
`manager_day_stats`, `manager_hour_stats`, пересчёт; экран «Мой день»: цифры дня, тепловая карта, блок месяца; поле `hire_date`, экраны планов и отсутствий.
*Чекпоинт:* цифры дня совпадают с amoCRM на 3 менеджерах.

**Этап 3. Оперативный пульт РОПа + воронки**
`/ops/board` (таблица, светофор, сортировки), вкладка воронок и конверсий (когортная/потоковая), командная тепловая карта, прогноз плана.

**Этап 4. Окупаемость и факторная диагностика**
`staff_costs`, `rop_cost_allocations`, `users.deactivated_at`, признак первой выручки (`client_key`, `is_first_revenue` + проверка истории клиента), экран `/ops/costs`, `/ops/payback`, waterfall‑разложение, сдвиг на цикл сделки, ограниченный вид для менеджера.

**Этап 5. Миссии и геймификация**
`daily_missions`, `manager_progress`, `xp_ledger` (+ миграция существующего XP), генерация целей, тиры, уровни, серии, заморозки, рекорды, анти‑накрутка, quality gate, вкладка «XP за неделю», командный квест, анимации.

**Этап 6. Уведомления, алерты, AI‑диагностика**
Telegram‑сообщения менеджерам (привязка чата через `/start` с одноразовым кодом из профиля), чекпоинты РОПу и встраивание в существующий пульс, `ops_alerts`, еженедельная AI‑диагностика и блок «Фокус недели».

## 16. Критерии приёмки модуля

1. РОП в любой момент рабочего дня за ≤ 10 секунд видит, кто из менеджеров работает, кто нет и кто отстаёт от нормы — без прослушивания звонков и без захода в amoCRM.
2. Менеджер при входе видит одну понятную цель дня и в среднем по команде берёт ≥ Bronze в 70 %+ рабочих дней (проверка через 4 недели эксплуатации).
3. По любому менеджеру за любой месяц есть payback и объяснение динамики в терминах факторов воронки.
4. Цифры модуля сходятся с amoCRM с расхождением ≤ 3 % по звонкам и этапам.
5. Ни один существующий экран и отчёт SalesOS не сломан.

## 17. Принятые решения (зафиксировано заказчиком)

1. **Встречи** — отдельные этапы воронки amoCRM («назначена», «проведена»). Задачи не используются.
2. **Сообщения** — менеджеры пишут клиентам через «Чаты» amoCRM; это полноценный источник касаний.
3. **Окупаемость** — только по первой выручке клиента; повторные оплаты не учитываются. Затраты вводятся вручную на странице `/ops/costs` для менеджеров и РОПа; затраты РОПа распределяются между активными менеджерами пропорционально отработанным рабочим дням.
4. **Мотивация** — XP, уровни, серии и бейджи нематериальные; к бонусам не привязываются.
5. **Выручка = только первая выручка от клиента** (продажи предоплатами на 6 и 12 месяцев). Повторные оплаты не учитываются нигде: ни в плане, ни в окупаемости, ни в XP и лидерборде.
